01Tese

Os conceitos da categoria — company, agent, issue, heartbeat, run, approval, budget, routine — implementados do zero em Go, num binário, com Postgres como única dependência de dados e observabilidade completa de fábrica. Nenhum código de terceiros. Nicho: operação on-prem em ambiente regulado, onde o cliente opera a infra e o DB.

REFERÊNCIA

O líder da categoria

~1,3M linhas TS · 68 tabelas · 342 migrations · 12 adapters · time full-time. Paridade é inviável solo — por isso escopo é governado por milestones, não por feature-list.

DIFERENÇA

Chato na infra, novo no domínio

Novidade vai em heartbeat, governança e budget. DB, fila e framework são escolhas conservadoras de propósito.

MODELO

Open-core

Core Apache-2.0 com DCO. ee/ reservado para features enterprise sob licença comercial. Core nunca precisa ser relicenciado.

02Princípios

Single binary

hanko sobe API + UI embutida + scheduler. Zero Node em runtime; Node só como ferramenta de build (dev/CI).

Postgres é a única dependência de dados

Sem Redis, sem fila externa. Fila, scheduler e domínio na mesma transação.

Observabilidade mandatória, zero phone-home

OTel sempre ligado — traces, métricas e logs correlacionados por run. Vai pro seu collector. Telemetria de produto não existe.

Code-first

Go é a fonte da verdade. OpenAPI é gerado, versionado e checado no CI.

Stdlib primeiro

Dependência só quando a stdlib não resolve. Sem ORM, sem framework HTTP.

Multi-org desde o dia 1

company_id em toda tabela de domínio desde a primeira migration.

Incremento visível por sessão

Toda sessão termina com algo executável + commit. Demo semanal. Escopo cede, prazo não.

Fronteira dura host/ilha

UI server-rendered; React só em folhas isoladas, com teto de 3.

04Arquitetura

Camadas: handler → service → store. Handler não toca DB; store não tem regra de negócio; domain não importa infra. Toda escrita de domínio gera activity_event na mesma transação — alimenta SSE, audit trail e budget. Todo request, job e run carrega trace_id; logs saem com ele.

Contrato host / ilha

  • Host decide rota, auth, layout, navegação, listas.
  • Ilha é folha: props via data-*, emite eventos ou chama a API. Nunca roteia, sem estado global.
  • Um CSS, mesmos tokens. Sem shadcn global.
  • Só esbuild. Sem Vite, pnpm workspace, Router, TanStack.
  • Teto 3 ilhas (log viewer, org chart, editor). A 4ª exige ADR.

07Alavancas de velocidade

Velocidade vem de três lugares: horas, paralelismo e corte de escopo. Não vem de pular testes em domain/heartbeat nem de "ir fazendo".

1

Contrato antes de código

Cada milestone abre com 1 sessão de migrations + tipos de domínio + OpenAPI. Só então 3 trilhas paralelas de agentes implementam contra o contrato — sem contrato, paralelismo vira merge hell.

2

Incremento visível por sessão

Toda sessão termina com algo executável + commit. Zero sessões "só refatorando". Regra em AGENTS.md.

3

MCP sai do M1

CLI já dá controle total. MCP entra no M2 junto com o dogfood, quando tem UI pra operar.

4

Demo semanal

Checkpoint toda semana, não só no fim do milestone. Vídeo curto, sem polish.

5

Qualidade onde importa

≥70% de cobertura só em domain e heartbeat. Resto best-effort até v0.1.

6

Horas são a alavanca-mestra

12 semanas → 8 só existe com ≥20 h/sem. Com 10 h, nenhuma alavanca acima compensa.

08Regras de parada

ESCOPO × PRAZO

Estourou 2x → corta escopo

Nunca estica prazo. O que não coube vai pro próximo milestone ou pro v0.2.

GATE M1

M1 não roda em 1 semana → para tudo

(2 semanas com <20 h.) Reavaliação completa: escopo, stack, horas. Sem exceção.

GATE M2

UI >50% das horas → reavalia D4

Se o host templ+htmx estiver custando mais que o domínio, a decisão de UI reabre.

ILHAS

4ª ilha exige ADR

Teto de 3 ilhas React e 3 JS vendorizados até v0.2.

DEMO

Sem demo gravada, milestone não fecha

Tag só depois do vídeo. Antídoto contra "pronto quando pronto".

DOGFOOD

A partir do M2, Hanko constrói Hanko

Lead-orchestrator + subagentes + crítico cego operando pelo próprio Hanko via MCP.

09Memória entre sessões

No desenvolvimento (nós)

  • Repo é a memória canônica: docs/ROADMAP.md (milestone aberto), docs/adr/ (decisões), docs/STACK.md, docs/SESSION.md (estado deixado pela última sessão: feito / travado / próximo).
  • AGENTS.md = protocolo de cold start para humano, Claude Code, Cowork e os próprios agentes do Hanko. Toda sessão começa lendo-o e termina atualizando SESSION.md.
  • Project "Hanko" no Claude guarda o resumo das decisões; memória do Project guarda contexto durável. Nenhum dos dois substitui o repo.

No produto (agentes do Hanko)

  • v0.1: instruções por agente versionadas; thread da issue como contexto do run; state_dir por agente para o adapter (sessão do CLI); activity_event como histórico auditável.
  • v0.2: memória de longo prazo (learnings entre runs) e sessão persistente via ACP.
