# Validação M20 — Etapas do projeto sobre as tasks e cards de status (ADR-0048)

Ramo `evolucao/m20`, a partir da `main` com M7–M16 e M15 mergeados. Itens #45 e #46 de `docs/PLANO-DECISOES.md`. Decisões e limites em
`docs/adr/0048-pipelines-de-tasks-e-cards-de-status.md`. Tudo contra fakes (`fake` como harness, `httptest` como endpoint do decision model): nenhuma
chamada real e nenhum custo.

## Já coberto (não refeito)

- **Pipelines de cases** (ADR-0034): continuam como estão e continuam sendo o menu "Pipelines". O #45 do plano é *outra coisa* — o pipeline **sobre tasks**,
  por projeto — e entrou como `project_stages` (na interface: **Etapas do projeto**), sem tocar nas tabelas de cases.
- **Gates, `task_review` e revisão automática** (ADR-0020/0040/0041): reaproveitados. O pipeline não criou tabela de gate nem de revisão; a etapa pede o gate
  existente e `afterGateDecided` ganhou um ramo para o gate que decide o avanço de uma etapa.
- **Cards de status** (ADR-0032): pergunta salva (interesse), persona resumidora, revisões imutáveis do resumo e arquivar/restaurar já existiam. O #46 acrescenta o
  motor `decision`, o modo `cron` e o resultado em artefato + Painel.
- **Decision model** (ADR-0056): reaproveitado como motor; a única mudança nele é a feature nova `card_summary` e o teto de tokens por feature (`featureRun.maxTokens`).
- **Memória governada** (ADR-0030): o aprendizado entra pelo mesmo outbox de fatos das decisões de gate; não há caminho novo de escrita livre.

## Como validar no hanko-prd

1. **Demo do roteiro: triagem → dev → review → QA sozinha, parando só nos gates.**
   ```
   hanko stage set site \
     --stage triagem:Triagem:todo:ana \
     --stage dev:Desenvolvimento:in_progress:bruno \
     --stage review:Review:in_progress:carla:approval \
     --stage qa:QA:in_progress:davi:review
   hanko task create "Página de preços" -p site            # nasce em Triagem, atribuída à Ana, e ela é acordada
   hanko stage show HNK-42                                  # etapa 1/4, working
   # a Ana conclui (hanko_stage_complete, ou hanko_task_update status=done); a task vai sozinha para o Bruno, depois para a Carla
   hanko gate list --status pending                         # só agora há algo para você: "Aprovar etapa Review"
   hanko gate request-changes <gate> -n "cite o arquivo alterado"   # a Carla é acordada com a nota; vira aprendizado
   hanko stage learnings site --stage review
   hanko gate approve <gate>                                # avança para o QA; o Davi conclui e o gate task_review (com a revisão automática, se houver) fecha a task
   ```
   Na tela: aba **Etapas** do projeto (`/c/<empresa>/projetos/site?secao=etapas`) e o painel **Etapa do projeto** na lateral da task.
2. **Card de status que atualiza de manhã.**
   ```
   hanko decision feature card_summary on                   # (precisa do decision model configurado: Configurações › Decision model)
   hanko status-card create "O que ficou bloqueado desde ontem?" --engine decision \
     --project site --open --cron "0 7 * * 1-5" --tz America/Sao_Paulo --dashboard
   hanko status-card refresh <id>                           # primeira atualização agora (a chamada é síncrona)
   hanko status-card show <id>                              # Motor: decision · cron 0 7 * * 1-5 · Artefato: card-….md
   hanko artifact list                                      # uma versão nova do card-….md por atualização
   ```
   O Painel (`/c/<empresa>/`) mostra o card com o resumo, a próxima atualização e o link do artefato. No dia seguinte, depois das 7h (fuso informado), uma versão nova do
   artefato aparece sem ninguém pedir; `hanko status-card show` mostra o gatilho `cron` no histórico.
3. **Falha visível.** Desligue a feature (`hanko decision feature card_summary off`) e rode `hanko status-card refresh <id>`: erro 422 com o motivo, o card fica `error`
   mantendo o último resumo; ligar de novo e atualizar o recupera.

## Riscos e limites

- Task criada por pessoa num projeto com etapas **perde a persona principal** em favor da persona da 1ª etapa (decisão do ADR-0048; escolher a persona ao criar vence).
- O motor decision faz a chamada HTTP dentro do tick, em sequência; muitos cards vencendo juntos alongam o tick. A trava consultiva evita dois ticks, e uma geração
  presa por mais de 10 min vira erro.
- O motor do card é imutável depois de criado (criar outro).
- A publicação do artefato roda depois do commit do resumo: se falhar (cota de artefatos, por exemplo) o resumo vale e a próxima atualização tenta de novo; só há aviso no log.
- `moveTask` zerava `tasks.model` ao mover por gate (bug existente); corrigido porque o pipeline move tasks por gate o tempo todo.
- Export/import (ADR-0022): as etapas não viajam (referenciam personas por id), como os pipelines de cases.

## Pulado/Falhou

- Nada pulado. Item sem versão "real": os dois motores foram exercitados contra fakes (`httptest` como endpoint OpenAI-compatível e o harness `fake`); a regravação com um
  endpoint e harnesses reais é parte da validação no hanko-prd.
