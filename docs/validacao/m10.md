## Como validar no hanko-prd

Pré-requisitos: `HANKO_GIT_WORKSPACES=true`, `HANKO_WORKSPACES_ROOT` definida, `git` no PATH, `HANKO_SECRET_KEY` se o repositório for privado.

1. **Ligar o Git.** Repositório privado: `printf %s "$TOKEN" | hanko secret create repo-token --value-stdin` (token com leitura do repo). Depois:
   ```
   hanko workspace create loja --path <raiz>/<empresa>/loja --repo https://github.com/<dono>/<repo>.git
   hanko workspace git enable loja --credential '${secret:repo-token}' --sync
   hanko workspace git show loja
   ```
   Esperado: `Espelho: ready`, branch base e commit; a credencial aparece só como `${secret:repo-token}`. UI: `/c/<empresa>/workspaces/loja?secao=git`. O valor do token não pode aparecer em lugar nenhum (log do servidor, atividade, erro de uma busca que falhe).
2. **Demo (task → branch → commit → diff → limpeza).**
   ```
   hanko project create "Loja online" --workspace loja
   hanko task create "Adicionar busca" -p ana --project loja-online
   ```
   Esperado: ao a persona começar, o log da run mostra `worktree Git: branch hnk-<n> em …/.hanko/worktrees/loja/hnk-<n>`. `hanko task git status HNK-<n>` mostra a branch, `À frente / atrás` e as alterações soltas; `hanko task git diff HNK-<n>` e `…/tasks/HNK-<n>/git?aba=diff` mostram o diff; `hanko task git log HNK-<n>` lista os commits da persona (autor = nome dela). `hanko task git ls|cat` navegam os arquivos (somente leitura). Ao concluir (`hanko task status HNK-<n> done`) a pasta some em até 5 min (ou `hanko task git clean`), e o diff/log/arquivos continuam navegáveis a partir do espelho.
3. **Integração.** Faça o merge da branch no remoto (fora do Hanko), `hanko workspace git sync loja`: `task git status` passa a mostrar `Integrada: true` e, na próxima rodada do tick, o worktree da task ainda aberta é limpo (`removed_reason=merged`) e a branch some do espelho.
4. **Divergência.** Entre no worktree, `git switch -c outra`, e peça outra run: o log avisa `worktree divergente` e a aba Git mostra o selo; volte para a branch e o estado normaliza. Apague a pasta do worktree: a próxima run recria reaproveitando a branch.
5. **Padrões do projeto.** `hanko project defaults loja-online --instructions "..." --goal <meta> --import-skills --skills-path .claude/skills`; uma task nova do projeto herda a meta e o system prompt da run traz "## Instruções do projeto" depois das instruções da persona. As skills do repositório aparecem em Skills › Fontes (origem "repositório do workspace"). Política de revisão: aba **Padrões** do projeto.
6. **Nova sessão.** `hanko task new-session HNK-<n> --reason "contexto confuso"` (ou o botão no painel da task). O próximo run mostra "Sessão nova" no briefing e a atividade registra `task.session_reset` e `run.session_reset_applied`.

## Riscos e limites conhecidos

- **Sem push.** O trabalho vive na branch do espelho; levá-lo ao remoto é manual (ou canais/GitHub, M-futuro).
- Janela de rebinding de DNS entre a checagem de host e a conexão do `git` (igual ao ADR-0035).
- Ambientes remotos (SSH/sandbox): o worktree é sincronizado como pasta comum e o `.git` dele aponta para o espelho deste servidor, então o git não funciona dentro do ambiente remoto (a run avisa).
- Serialização de espelho só dentro do processo; entre processos vale o lock do próprio git.
- `HANKO_GIT_WORKSPACES` precisa estar ligado também para a **limpeza** acontecer (o tick não roda desligado); desligar com worktree vivo deixa a pasta até religar ou excluir o workspace.
- Política de plano de projeto (#19) pendente do gate de plano. Export/import não leva configuração Git, worktrees, padrões de projeto nem pedidos de nova sessão.
- A UI foi validada por testes de handler/HTML (sem navegador real nem screenshot); o CSS ganhou só classes `.git-*`, as ilhas não foram reconstruídas.

## Pulado/Falhou

Nada falhou duas vezes; nada revertido. Pulado: política de plano do projeto (#19), pelo motivo acima.
