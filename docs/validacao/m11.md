# Validação M11 — Ambientes de execução, readiness, catálogo de modelos (ADR-0055)

Ramo `evolucao/m11`. Itens #35, #10 e #17 de `docs/PLANO-DECISOES.md`. Decisões, critério de escolha do provider cloud e limites em
`docs/adr/0055-ambientes-readiness-catalogo-de-modelos.md`. Parte do que o ADR-0037 (ambientes SSH e sandbox) já entregou: **já
coberto por ADR-0037** e não refeito aqui: tabela `environments`, drivers `ssh` e `sandbox` (docker), atribuição por persona e padrão da
empresa, segredos cifrados do ambiente, `${secret:X}` nos valores de `env` do ambiente (ADR-0050, M7), tela Configurações ›
Ambientes, `hanko env`.

## Como validar no hanko-prd

Pré-requisito: empresa com uma persona fake (`ana`) e `HANKO_URL`/`HANKO_TOKEN`/`HANKO_COMPANY` apontando para a instância.

1. **Mesma persona, três lugares (demo).**
   ```
   hanko env create servidor --driver local --env DA_LOCAL=sim
   hanko env create caixa --driver sandbox --image alpine:3 --network bridge     # precisa de HANKO_ENV_SANDBOX=docker e do docker
   hanko env create build --driver ssh --host build.exemplo.com --user hanko --root /srv/hanko --known-hosts-file kh --key-file id --probe
   hanko persona update ana --environment servidor        # roda local (explícito)
   hanko persona update ana --environment caixa           # roda em contêiner
   hanko persona update ana --environment build           # roda via SSH
   hanko task create "Teste" -p ana && hanko run list && hanko run show <run>   # "Ambiente (origem): … persona"
   ```
   Esperado: o log da execução abre com "executando no ambiente …" e a tela da execução mostra "origem: da persona".
   Sem docker/SSH reais, o equivalente automatizado é `TestSamePersonaRunsEverywhere` (local, docker com cliente fake, ssh com `ssh`
   fake e cloud com a API fake).
2. **Precedência.** `hanko env default build`; `hanko project env site servidor`: uma task do projeto `site` roda em `servidor`
   (`origem: do projeto`); uma task sem projeto roda em `build` (`padrão da empresa`); `hanko persona update ana --environment caixa`
   faz a persona vencer o projeto. `hanko env rm servidor --move-to build` leva persona e projeto.
3. **Probe e capacidades.** `hanko env probe build` → passos `connect`, `system`, `workspace_root`, `bin:*`, `hanko_url` e a linha
   "Capacidades: …". Em Configurações › Ambientes o relatório mostra os chips.
4. **Readiness: auth quebrada aparece antes do run.** Numa persona `claude` num host sem login:
   `hanko persona test ana` → `NÃO PRONTA`, passo `auth` com a dica (`claude auth login`), sai com erro. A Caixa de entrada ganha o
   alerta `persona_not_ready` no próximo `alert_tick`, e `hanko task create "x" -p ana` não abre execução (o wake registra
   "persona não pronta"). Faça o login no host (ou ponha `ANTHROPIC_API_KEY` no env da persona) e rode `hanko persona test ana` de
   novo: pronta, alerta fecha, a task roda. Na UI: contratar uma persona leva à página dela com o cartão **Prontidão do harness**
   testando sozinho; **Testar agora** repete.
5. **Catálogo.** `hanko model list --agent claude` mostra `opus/sonnet/haiku`, linhas de `model_prices` e o que já rodou, com "sem preço"
   onde não há prefixo. Em Personas › Contratar o campo Modelo é um select com "Outro…" (mostra o campo livre) e o aviso de preço.
6. **Cloud (precisa de conta Daytona).** `HANKO_ENV_CLOUD=daytona`, `HANKO_ENV_CLOUD_SSH_KNOWN_HOSTS="$(ssh-keyscan ssh.app.daytona.io)"`,
   `hanko env create nuvem --driver cloud --api-key-file chave.txt`, `hanko env probe nuvem`. **Não foi possível validar sem rede e sem
   credencial**: o contrato real (rotas, campos, autenticação do gateway por token) segue a documentação pública conhecida e foi
   exercitado só contra um servidor de teste. Se divergir, o ajuste é local a `internal/execenv/daytona.go`.

## Testes (o que cobre o quê)

- `internal/domain`: propriedade da precedência (`TestChooseEnvironmentProperty`, 2000 sementes) + tabela; readiness, catálogo e
  `MatchPrice` (cobertura 95%).
- `internal/execenv`: `DockerClient` fake (argv endurecido, env fora do argv, `kill`/`rm`), `RunScript` em local/ssh/docker/cloud,

## Riscos e limites conhecidos

- Cloud não validado contra o provider real (ver acima). O gateway SSH do Daytona autentica pelo token no usuário, sem chave: o ssh roda
  com `BatchMode` e `StrictHostKeyChecking=yes`, então o `known_hosts` do operador precisa estar correto.
- O probe de readiness não chama o modelo (não gasta tokens): um modelo com nome válido mas inexistente só falha na primeira execução.
- A checagem periódica executa `sh` e `claude auth status`/`codex login status` no host do servidor (persona local) a cada intervalo por
  persona; é barato, mas é um processo filho a mais. `HANKO_READINESS_INTERVAL=0` desliga.
- O readiness testa o ambiente da persona (persona > padrão), não o do projeto: uma persona que roda em ambientes diferentes por
  projeto só é testada no dela.
- Um bloqueio por readiness vale até o próximo teste: consertado o login, o "Testar agora" ou a próxima passada (≤ intervalo) libera.
- O wake de uma persona não pronta é recusado em silêncio (log `info`) e repetido pelo heartbeat a cada tick; o sinal para o humano é o alerta.
- A UI foi validada por testes de handler/HTML (`uitest.Fake`), sem navegador real; o CSS só ganhou `.model-picker` (seletor `:has`).
  As ilhas React não foram tocadas.
- Outros marcos que estendam `alerts_kind_check` ou `environments_driver_check` conflitam na migration: recriar a constraint com a lista completa.

## Pulado/Falhou

- Nada pulado. Nenhuma fatia foi revertida.
- Fora do M11 por decisão do ADR: provider de ambiente via plugin (M18), listar modelos por API de provider (sem rede/credencial) e imagem
  custom para o sandbox (o plano diz "depois").
