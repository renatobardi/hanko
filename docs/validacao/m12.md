# Validação do M12 — Decision model e harnesses (ADR-0056)

Itens do plano: **#27** (decision model por empresa) e **#43** (harnesses). Ramo `evolucao/m12`.

## O que entrou

- **Decision model** (`internal/provider`, `internal/decision`, `internal/service/decision.go`): cliente de endpoint compatível com chat
  completions (stdlib), catálogo de modelos, três features registradas (triagem, classificador de fase, nome e resumo), ledger de
  invocações com ator `system` e `activity_event` na mesma transação. API, CLI e tela Configurações › Decision model; bloco "Decision
  model" no Custos; o custo soma ao gasto mensal da empresa (a query `SpendBetween` da empresa passou a incluí-lo).
- **Harnesses** em `internal/adapter`: `devin` (ACP de comando fixo, `acp.NewFixed`), presets ACP `gemini` e `opencode`, `pi`, `cursor`
  (esqueleto comum `cliharness`) e `http` (`httpagent`: loop de tool-use + cliente MCP do SDK que o servidor já usa).
- **Probe** de prontidão (`adapter.Prober`): acp/devin (handshake sem prompt), pi/cursor (`--version`), http (`GET /models`).
  Endpoint `POST /companies/{c}/personas/{p}/probe` e `hanko persona probe`.
- Contratação: cartões Devin, Pi, Cursor e HTTP na tela; preset ACP; campos de endpoint e chave do http. Configurações › Adapters mostra
  os quatro harnesses novos.

## Como validar no hanko-prd

1. **Decision model.** Em Configurações › Segredos crie `openrouter` (a chave real do OpenRouter). Em Configurações › Decision model:
   endpoint em branco, chave `${secret:openrouter}`, um modelo barato do catálogo (digite o id; o datalist lista o catálogo depois de
   salvar). Esperado: "Decision model salvo." Ligue **Triagem**. Pela CLI: `hanko decision catalog | head`, `hanko decision show`.
2. **Triagem.** Crie uma task sem responsável e rode `hanko decision triage HNK-N`. Esperado: comentário do sistema na task com a
   persona e a prioridade sugeridas (nenhuma atribuição); `hanko decision invocations` mostra a linha (tokens, custo, `reported` ou
   `estimated`).
3. **Custos.** Em `/c/<empresa>/custos` aparece o bloco "Decision model" com a feature e o modelo; `hanko cost` / `GET /costs` traz
   `decision`. O orçamento da empresa do mês passa a incluir esse custo.
4. **Devin.** Instale/autentique o `devin` no servidor. `hanko persona hire "Dev" --agent devin` e `hanko persona probe dev`: esperado
   passos binário/protocolo/autenticação verdes; sem login, "autenticação" falha com os métodos anunciados. Atribua uma task e confira a
   run (permissão padrão `read_only`; use `--config permission=allow` para editar).
5. **Pi** (`--agent pi`) e **Cursor** (`--agent cursor`): a CLI `hanko` precisa estar no PATH do servidor. Atribua a mesma task e confira
   que a persona comenta na task pela CLI (o run token vira `HANKO_TOKEN` só no processo do harness).
6. **HTTP.** `hanko persona hire "Op" --agent http --model <modelo> --config-json '{"base_url":"https://openrouter.ai/api/v1","api_key_ref":"${secret:openrouter}"}'`,
   `hanko persona probe op` e uma task: o log mostra `tool_use`/`tool_result` das tools `hanko_*`. Com oMLX: `base_url` do Mac
   (`integrations.allow_private` ligado), reabrindo o teste do plano.
7. **Mesma task em três harnesses** (demo): Devin, Pi e uma persona HTTP rodam a mesma task; a triagem (passo 2) usa o decision model.

## Riscos e limites conhecidos

- **Formatos de Pi e Cursor.** As fixtures foram escritas a partir da documentação dos eventos, não gravadas de um binário real (não há
  binário nem rede aqui). O parser ignora o que não conhece, mas se o formato real divergir a run sai "sem resposta". Regravar com os CLIs
  reais é parte desta validação. As flags (`--mode json -p`, prompt pelo stdin; `cursor-agent -p --output-format stream-json`, `--resume`,
  `--force`) também são suposições a confirmar.
- O `devin acp` e as flags `gemini --experimental-acp` / `opencode acp` seguem a documentação dos presets, também sem binário real.
- Pi/Cursor não têm `hanko_gate_request` pela CLI: o protocolo manda comentar e marcar `blocked`.
- O harness `http` só usa as tools do servidor MCP do Hanko (`hanko`); não conecta MCPs de integrações da empresa, não executa comandos
  e não retoma sessão.
- Triagem é acionada por API/CLI; não roda sozinha na criação da task (evita gasto não pedido). Fast responses ficam com canais (#42).
- O probe periódico e o bloqueio de despacho por readiness (#10) não fazem parte deste marco: só a primitiva e o botão/CLI de teste.
