## Como validar no hanko-prd

1. **Demo do roteiro: pergunta → plano → mudança → reenvio com diff.**
   ```
   hanko plan-policy set ana --scope persona --on                 # a Ana só executa com plano aprovado
   hanko task create "Publicar a release 1.4" -p ana
   # a Ana (fase de planejamento) pergunta antes de planejar:
   #   hanko_gate_request kind=question questions=[{key:"janela",label:"Janela de deploy?",type:"single",options:[...]}]
   hanko gate list --kind question --status pending               # ou /c/<empresa>/caixa
   hanko gate answer <gate> --set janela=noite                    # (ou o formulário na tela do gate)
   # a Ana acorda com a resposta na thread, publica plano.md e pede hanko_gate_request kind=plan artifact=plano.md
   hanko gate request-changes <gate-do-plano> -n "falta o rollback"
   # a Ana publica a v2 do plano e reenvia: hanko_gate_resubmit id=<gate> artifact=plano.md note="acrescentei o rollback"
   hanko gate history <gate-do-plano>                              # revisão vigente 2, a nota da devolução e o diff (+ linhas novas)
   hanko gate approve <gate-do-plano>                              # a próxima run executa com "## Plano aprovado (revisão 2)" no briefing
   ```
   Na tela: `/c/<empresa>/gates/<id>` mostra o formulário (radio/checkbox/texto, Responder, Dispensar), depois as respostas; o plano reenviado mostra
   "Reenvios (revisão 2)" com o diff e as versões anteriores.
2. **Fase de plano só-leitura.** Durante a fase `plan`, uma tool de escrita do Hanko (`hanko_task_update`, `hanko_task_create`, `hanko_goal_update`...) responde
   "esta execução só planeja"; no claude, a run roda com `--permission-mode plan --disallowedTools Edit Write NotebookEdit`; no codex, `--sandbox read-only`.
   `hanko plan-policy show <task>` mostra as camadas, a origem e a fase (`plan` → `execute` depois da aprovação).
3. **Audiência.** Um gate com `audience` (`roles:["admin"]` ou `users:[…]`) some da Caixa de quem não está nela e responde 403 a quem tenta decidir; o owner sempre decide.
4. **Contratação por gate.** `hanko_hire_request name=Yuki agent=claude …` (ou `hanko persona hire Yuki --agent claude --gate`): o gate mostra a "Ficha da contratação";
   aprovar cria a Yuki, reportando a quem pediu, e registra `persona.hired` com `via_gate`. `hanko company policy hire-gate=on` (owner) faz o `persona hire` direto responder 409.
5. **Persona principal e de sistema.** Logado: `hanko persona primary ana`; `hanko task create "x"` (sem `-p`) nasce com a Ana. Como owner: `hanko persona system ana`; um admin
   recebe 403 ao editá-la e ninguém a desliga (409).
6. **Incidente de orçamento.** `hanko budget set 1 --persona ana` e uma run que passe de US$ 1: `/c/<empresa>/caixa?aba=orcamento` e `hanko budget incidents` mostram o incidente;
   `hanko budget resolve <id> --once` libera um run (o seguinte volta a ser barrado), `--raise 20` sobe o teto e retoma a persona pausada por orçamento, `--keep` só registra.

## Riscos e limites conhecidos

- A fase de plano é imposta de verdade em **claude** (modo plan) e **codex** (sandbox read-only) e, para qualquer harness, nas tools de escrita do Hanko (servidor).
  Em **ACP** (e em qualquer harness sem modo somente leitura) ainda é possível escrever arquivos locais: o `Spec.PlanOnly` não altera a política de permissão do ACP, para
  não bloquear as tools MCP que publicam o plano. O prompt pede só planejamento; o limite está registrado no ADR-0041.
- "Revisão automática roda de novo" no reenvio: vale para `task_review` pelo caminho já existente (nova tentativa de fechar a task abre novo gate e nova revisão); o
  reenvio no mesmo gate cobre `approval`, `plan` e `hire` sem revisão automática (esses tipos nunca tiveram uma).
- `liberar só este run` num teto de **projeto** concede o crédito, mas não acorda tasks já recusadas: a rede de segurança do heartbeat as retoma na próxima passada.
- A decisão de um gate `instruction` de uma persona de sistema segue exigindo só admin (a guarda de owner está na edição direta e na restauração de revisão).
- Nenhuma persona é marcada como de sistema por backfill; o owner escolhe.
- Glossário (`docs/GLOSSARIO.md`/`docs/en/GLOSSARY.md`) não foi editado neste marco (evita conflito de merge); termos novos: *pergunta*, *plano*, *incidente de orçamento*,
  *persona principal*, *persona de sistema*.
