# Validação M9 — Política de tools e gateway (ADR-0053)

Ramo `evolucao/m9`. Itens #20, #39 e #40 de `docs/PLANO-DECISOES.md`. Decisões e limites em `docs/adr/0053-politica-de-tools-e-gateway.md`.

## Já coberto por ADR-0036 (não refeito)

Catálogo de tools por integração (`tools/list`), risco pelas anotações, **quarentena** de tool nova/alterada que escreve, perfis reutilizáveis
(regras include/exclude, allow/ask) com vínculos empresa/projeto/persona, gateway da run `/mcp/run/{integração}`, gateway nomeado com token
`hkgw_` por cliente externo (ações, expiração, revogação), gate `tool` com aprovação de uso único, auditoria `tool_invocations` (decisão, status,
latência, sha256) e as abas Tools/Perfis/Gateways/Auditoria. O gate continua `kind=tool` (o plano chama de `tool_call`); `gates_kind_check` não foi tocada.

## Env e flags novas

- `HANKO_TOOLS_SINGLE_ENDPOINT` (`tools_single_endpoint` no yaml), padrão `false`: o harness recebe um servidor MCP `hanko-tools` (`/mcp/run`) em vez de um por integração.
- CLI: `hanko tool-policy list|set|delete`, `hanko integration tools <i> --test <tool> --as <persona> [--args JSON] [--execute]`, `hanko gate approve --always`, `hanko hook pretooluse` (uso interno).
- Nenhuma dependência Go nova.

## Como validar no hanko-prd

Pré-requisitos: uma empresa com uma persona (`ana`), uma integração MCP http (`docs`) com `HANKO_INTEGRATIONS_ALLOW_PRIVATE` se for interna,
catálogo descoberto (`hanko integration tools docs --refresh`) e `HANKO_URL`/`HANKO_TOKEN` na CLI.

1. **Demo: ask → sempre → direto → log.**
   ```
   hanko tool-policy set ask --persona ana --integration docs --tool apagar
   hanko integration tools docs --test apagar --as ana                  # simulação: "pediria aprovação"
   hanko task create "apagar o rascunho" -p ana                         # a persona chama docs/apagar
   hanko gate list --kind tool --status pending                         # o gate da chamada (Caixa › Tools)
   hanko gate approve <gate> --always                                   # admin: aprova e grava a política
   hanko tool-policy list --persona ana                                 # docs/apagar → permitida (sempre permitir)
   hanko task create "apagar outro" -p ana                              # passa direto, sem gate novo
   ```
   Auditoria em `/c/<empresa>/ferramentas/auditoria` (ou `GET …/tool-invocations?persona=ana`): a primeira linha `perguntar antes`, as seguintes
   `permitida` com origem `policy:persona`, ator, duração e o trecho do resultado.
2. **Testar como a persona X.** Aba **Política** em `/c/<empresa>/ferramentas/politica`, formulário "Testar uma tool como uma persona": simulação
   mostra estado, veredito e origem; "Chamar de verdade" repassa e audita como `teste`. `hanko integration tools docs --test ler --as ana --execute`.
3. **Quarentena na Caixa.** Faça o servidor expor uma tool nova que escreve e `hanko integration tools docs --refresh`; `/c/<empresa>/caixa?aba=tools`
   mostra "Tools em quarentena" (só admin) até `hanko integration tools docs --review`.
4. **Tool nativa (claude).** `hanko tool-policy set ask --native Bash --persona ana`; uma run do claude da Ana que use `Bash` abre um gate `tool`
   (corpo com o comando, credenciais mascaradas) e fica esperando até 10 min; aprovar libera a tool, rejeitar (ou o prazo) nega. O log da run mostra
   a negação. A auditoria mostra `hook` como origem. Em ACP o mesmo vale por `session/request_permission` (tipo `execute`, `edit`...).
5. **Prazo do gate.** Deixe um gate nativo sem decisão por mais de 10 min (ou um de integração por mais de 24 h): aparece em Gates › Rejeitados como
   `expired`, com `gate.expired` na atividade; a mesma chamada abre um gate novo.
6. **Endpoint único.** Com `HANKO_TOOLS_SINGLE_ENDPOINT=true`, o `mcpServers` da run passa a ter `hanko-tools` em `/mcp/run` e as tools saem como
   `docs__ler`; a política é a mesma.

## Riscos

- Política `allow` na empresa vence o perfil da persona nas runs (é exceção explícita de admin); o gateway nomeado não sofre isso.
- O hook do claude depende do executável `hanko` local e do run token no ambiente do harness; não vale em ambiente remoto (aviso no log).
- A espera do gate nativo ocupa a run (e o worker) por até 10 min.

## Pulado/Falhou

- **Um único servidor para Hanko + integrações + plugins** (#40): parcial. O endpoint único cobre só as integrações MCP http; `hanko_*` e plugins seguem
  em `/mcp` (contrato de nomes dos prompts). Detalhe e motivo no ADR-0053, §5.
- **codex** não tem gancho de permissão por tool: a política vale só para integração e plugin nele.
- Export/import não leva políticas (como perfis e vínculos no ADR-0036).
