# Validação M18 — Plugins: contribuições, capacidades e SDK (ADR-0045)

Ramo `evolucao/m18`. Item #37 de `docs/PLANO-DECISOES.md`. Parte do que o ADR-0038 já entregou no v0.3 (processo isolado, manifesto,
capacidades, tools, eventos, jobs, widgets, estado, segredos, API/CLI/UI) e implementa só a diferença.

## O que entrou

| Pedido do #37 | Entrega |
|---|---|
| Executável + manifesto + capacidades + JSON-RPC por stdio; tools | **Já coberto por ADR-0038** (nada a fazer). |
| Admin concede capacidades | `SetPluginCapability` (dono da instalação): conceder só o que o manifesto declara, revogar vale na hora; `admin_audit` + atividade das empresas. API `POST /plugins/{p}/capabilities/{c}/grant|revoke`, CLI `hanko plugin cap`, UI. |
| Páginas/abas em iframe sandboxed + ponte postMessage | Capacidade `pages`; `get_page`/`page_call`; documento do iframe com CSP sem rede e sem `allow-same-origin`; `window.hanko.call`; script da hospedeira em `/static/plugin-frame.js`; grupo "Plugins" na barra lateral; API `plugin-tabs` e `pages/{page}/call`; CLI `hanko plugin tabs`. |
| Gatilhos de fluxo | Capacidade `flows.trigger`; método do host `flows.fire`; tabela `plugin_flow_triggers` (migration 00140); API/CLI/UI para o admin ligar gatilho a fluxo. |
| Provider de ambiente (#35) | Capacidade `environments.provider`; `cloud.provider = plugin:<id>/<key>`; `execenv.Config.CloudPlugins`; `env.ping|create|ssh|delete`; ambiente exige o plugin ligado na empresa. |
| Fonte de skill (#36) | Capacidade `skills.source`; URL `plugin://<id>/<key>`; `skills.snapshot`; reaproveita `skill_sources` (sync, seleção, fork, pin) sem depender de `HANKO_SKILL_SOURCES`; API `plugin-skill-sources`. |
| enable/disable/remove | **Já coberto por ADR-0038** (por empresa e na instalação; desinstalar agora apaga também as ligações de gatilho). |
| SDK Go + `hanko plugin new` | `sdk/plugin` (só stdlib), `examples/plugins/showcase`, `hanko plugin new` (esqueleto validado pelo `ParsePluginManifest`). |

## Migrations aplicadas

`00140_plugins_m18.sql` (tabela `plugin_flow_triggers`). Aditiva; o Down a remove. `gates_kind_check` **não** muda.

## Env e flags novas

Nenhuma variável de ambiente nova (`HANKO_PLUGINS_DIR` / `HANKO_PLUGINS_DATA_DIR` seguem). CLI nova: `hanko plugin cap grant|revoke`,
`hanko plugin tabs`, `hanko plugin trigger list|link|unlink`, `hanko plugin skill-sources`, `hanko plugin new`.

## Como validar no hanko-prd

1. **Demo do marco (uma tool e uma aba; revogar tira):**
   `cd examples/plugins/showcase && go build -o showcase . && cp -r . $HANKO_PLUGINS_DIR/showcase`; `hanko plugin install showcase`;
   `hanko plugin enable showcase --company <empresa>`. Resultado: o grupo "Plugins" da barra lateral ganha **Showcase**; a persona
   enxerga a tool `plugin_showcase_ping`. `hanko plugin cap revoke showcase pages` tira a aba (e a página responde 404);
   `hanko plugin cap revoke showcase agent.tools` tira a tool; `hanko plugin cap grant …` traz de volta.
   Automatizado: `go test -tags integration -p 1 -run TestPluginShowcaseToolTabAndRevocation ./internal/service`.
2. **Ponte e gatilho:** na aba Showcase, "Registrar pedido" incrementa o contador (estado do plugin). Crie um fluxo e ligue:
   `hanko plugin trigger link showcase novo-pedido <fluxo> --company <empresa>`; clicar de novo cria a task do fluxo.
   Fluxo desligado é pulado. Teste: `TestPluginFlowTriggers`.
3. **Isolamento da aba:** no navegador, a aba é um `iframe` com `sandbox="allow-scripts"`; no console da página do plugin,
   `fetch('/api/v1/companies')` falha (CSP `default-src 'none'`) e `document.cookie` é vazio. Testes: `TestPluginFrameIsolation`,
   `TestPluginBridge`.
4. **Fonte de skills:** `hanko plugin skill-sources` lista `plugin://showcase/catalogo`; `hanko skill source add plugin://showcase/catalogo`
   importa a skill "Checklist de pedido". Teste: `TestPluginSkillSource`.
5. **Provider de ambiente:** um plugin com `environment_providers` + `environments.provider` aparece em `hanko plugin list`
   (`plugin:<id>/<key>`); `hanko env create "Nuvem X" --driver cloud --provider plugin:<id>/<key> --api-key-file -`. Testado com runtime fake
   (`TestPluginEnvironmentProvider`) e com sessão SSH de ponta a ponta (`TestCloudPluginProviderSession`, ssh e sandbox fakes).
6. **Esqueleto:** `hanko plugin new meu-plugin && cd meu-plugin && go mod tidy && go build -o meu-plugin .`.

## Riscos

- **Código do plugin roda no navegador** de quem abre a aba (isolado: origem opaca, sem cookies, sem rede, sem DOM do Hanko). Muda a
  regra "nenhum HTML de plugin chega ao navegador" do ADR-0038 **só** para `pages`, que exige a capacidade e vem sinalizada na
  tela de instalação. Os widgets continuam sendo só dados.
- `environments.provider` entrega a **chave de API do ambiente** ao plugin a cada chamada; a capacidade é destacada como de atenção.
- O `go.mod` do esqueleto não fixa a versão do SDK (o módulo público ainda não tem tag com `sdk/plugin`): `go mod tidy` resolve.
- O gatilho de fluxo não é deduplicado pelo host (cada `flows.fire` é um disparo).
- O M19 (#23) traz gatilhos por webhook e por evento interno para fluxos; o gatilho de plugin deste marco é independente e continua
  valendo (um plugin pode ser a origem do evento).

## Pulado/Falhou

- **Provider de ambiente no exemplo `showcase`:** não incluído (um provider de brinquedo seria enganoso); coberto por testes com
  runtime fake e documentado em `docs/PLUGINS.md` (seção 12) e no SDK (`plugin.EnvProvider`).
- **"Admin" que concede capacidades = dono da instalação**, não admin de empresa (decisão registrada no ADR-0045, item 2): o plugin
  é código na máquina do servidor.
- **Ícone da aba:** o `icon` do manifesto é validado e exposto na API, mas a barra lateral usa o ícone genérico de plugin.
- **Testes não executados:** nenhuma chamada a provider de nuvem real (por regra); o iframe foi exercitado só por testes de
  cabeçalho/HTML (sem navegador real nesta sessão).
