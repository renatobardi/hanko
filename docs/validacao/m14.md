## Como validar no hanko-prd

Pré-requisito: empresa com uma persona (`ana`) e `HANKO_URL`/`HANKO_TOKEN` apontando para a instância.

1. **Quebrar em três com dependência (demo).**
   ```
   hanko task create "Entregar a feature" -p ana                       # pai (HNK-1)
   hanko task create "A: modelar"     -p ana --parent HNK-1            # HNK-2
   hanko task create "B: implementar" -p ana --parent HNK-1 --depends-on HNK-2   # HNK-3
   hanko task create "C: validar"     -p ana --parent HNK-1 --depends-on HNK-3   # HNK-4
   hanko task show HNK-3                                               # BLOQUEADA: 1 dependência(s) aberta(s)
   ```
   Esperado: só a HNK-2 recebe execução (`hanko run list`). Na UI `/c/<empresa>/tasks/HNK-3`: breadcrumb `HNK-1 ›`, chip "Aguarda dependências", bloco Dependências com HNK-2.
2. **Cascata.** `hanko task status HNK-2 done` → a HNK-3 ganha execução (fato `task.unblocked` na atividade); `hanko task status HNK-3 done` → HNK-4; ao fechar a HNK-4 o pai (HNK-1) é acordado (`task.children_done`). Antes disso, `hanko task status HNK-1 done` deve falhar (422 com as subtasks abertas) e `hanko task status HNK-1 done --force --reason "teste"` conclui e registra `task.close_override`.
3. **Ciclo.** `hanko task dep add HNK-2 HNK-4` → 409 com a cadeia `HNK-2 → HNK-4 → HNK-3 → HNK-2`.
4. **Pausar o pai congela tudo.** `hanko task hold HNK-1 --reason "freeze"`; criar `hanko task create "D" -p ana --parent HNK-1` e conferir que **nenhuma** execução abre (`hanko run list --task HNK-5` vazio); `/c/<empresa>/tasks/HNK-5` mostra o banner "Pausada · herdada de HNK-1"; `/c/<empresa>/caixa?aba=pausadas` lista a HNK-1 com **Retomar**. `hanko task resume HNK-1` (ou o botão) → a HNK-5 recebe execução.
5. **Política de revisão.** `hanko task review-policy HNK-5 --require --no-reviewer` (admin); a persona que tentar fechar a HNK-5 cai em `in_review` com gate direto. Em `/c/<empresa>/execucoes/<run>` a linha "Política de revisão" mostra `obrigatória (origem: task)`. `hanko task review-policy HNK-5 --clear` volta a herdar.
6. **MCP.** Numa execução, `hanko_task_dependency` (`action=add|remove|list`) e `hanko_task_create` com `depends_on`.

## Riscos e limites conhecidos

- Pausa não mata run em andamento (só cancela as que ainda estão na fila). Decisão registrada no ADR.
- Janela transitória: um checkout que lê "sem dependência" no mesmo instante em que outra transação adiciona uma dependência pode abrir uma run para uma task que acabou de ficar bloqueada. Não há perda de dado; a run seguinte já é recusada.
- Deadlock residual (raro): pai e filho que **dependem** um do outro fechando em transações simultâneas; o Postgres aborta uma delas (erro 500, repetir resolve). Não há retry automático.
- Export/import (`hanko.company.v1`) leva a árvore, mas não dependências, pausas nem políticas por task.
- A política de revisão no projeto existe só via API/CLI (`project review-policy`); a tela de defaults de projeto do M10 deve reaproveitar `project_review_policies` (não criar colunas novas) para não conflitar.
- A UI foi validada por testes de handler/HTML (sem navegador real nem screenshot); o CSS não foi alterado (só classes existentes), então as ilhas não foram reconstruídas.
- Persona não pausa nem retoma; só humano com papel member+. Alterar política de revisão exige admin.
