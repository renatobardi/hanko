# Architecture Decision Records: index

An ADR wins over `docs/STACK.md` when they conflict. Add a new ADR instead of reopening a decision. All ADRs below are accepted.

| ADR | Title | Decision |
|---|---|---|
| [0001](../../adr/0001-reescrita-em-go.md) | Implementation from scratch in Go | Hanko implements the category's concepts from scratch as a single Go binary, with no third-party code. |
| [0002](../../adr/0002-escopo-v01-milestones.md) | v0.1 scope: full core in 6 milestones with gates | v0.1 ships the full core (org chart, approvals, budget, flows, UI), cut into milestones M1-M6 that each end with a recorded demo and a tag. |
| [0003](../../adr/0003-licenca-apache-dco.md) | Apache-2.0 + DCO; `ee/` reserved | The core is Apache-2.0 with a DCO sign-off and no CLA; `ee/` is reserved for enterprise features under a commercial license. |
| [0004](../../adr/0004-adapter-cli-primeiro-acp-depois.md) | `cli` adapter first, ACP in v0.2 | v0.1 runs agents through an `Adapter` interface with CLI engines (`claude`, `codex`); ACP over stdio comes in v0.2 (done: ADR-0023). |
| [0005](../../adr/0005-ui-host-templ-htmx-ilhas-react.md) | UI: templ + htmx host, React islands | The UI is a server-rendered templ + htmx host, with React islands (bundled by esbuild through Go) allowed only as leaves; an addendum (2026-10-14) replaces Tailwind with the project's own CSS built on Kubo DS tokens. |
| [0006](../../adr/0006-api-code-first-huma.md) | Code-first API with huma | Go structs define the API through huma, which generates and versions `api/openapi.json`; CI fails on an uncommitted diff. |
| [0007](../../adr/0007-auth-v01.md) | Auth v0.1: `local` and `firebase` providers | Two modes, `trusted` and `authenticated`; in `authenticated` the login provider is `local` (argon2id, cookie) or `firebase`, plus hashed API keys and short run JWTs. |
| [0008](../../adr/0008-deploy-oute-server.md) | Deploy on LXC at oute-server | `hanko-stg` and `hanko-prd` run as LXC containers on the owner's server with Compose, daily `pg_dump` + restic backups and a monthly restore test. |
| [0009](../../adr/0009-cadencia-milestones.md) | Cadence: short milestones, recorded demos | Milestones are short and end with a recorded demo; scope is variable and the deadline is not, and speed comes from hours, parallel tracks and cutting scope, not from skipping tests. |
| [0010](../../adr/0010-multi-org-dia-1.md) | Multi-org from M1 via `company_id` | `company_id` is on every domain table from the first migration; no RLS and no schema-per-tenant in v0.1. |
| [0011](../../adr/0011-postgres-unica-dependencia.md) | PostgreSQL 17 is the only dependency | PostgreSQL 17 is the only mandatory dependency (a document-database alternative was rejected); ai-memory is an optional, degradable dependency added by ADR-0015. |
| [0012](../../adr/0012-fila-river.md) | Queue and scheduler: river on Postgres | `river` provides the wakeup queue, retries, periodic jobs (flows) and unique jobs (heartbeat coalescing) inside Postgres, with no Redis. |
| [0013](../../adr/0013-otel-mandatorio.md) | Complete, mandatory OpenTelemetry | OpenTelemetry instrumentation (traces, metrics, correlated logs) is always on and exports to the operator's collector; product telemetry and phone-home do not exist. |
| [0014](../../adr/0014-auth-provider-firebase.md) | `firebase` auth provider | The `firebase` provider lets the browser sign in with Google or email/password and the server validates the ID token against Google's public keys before opening its own session; `local` stays the self-host default. |
| [0015](../../adr/0015-memoria-ai-memory-provider.md) | Memory: ai-memory on by default | ai-memory is on by default for both personas (MCP + hooks per run) and Hanko itself (briefing at dispatch, facts written through a Postgres outbox), and it degrades without data loss when unavailable. |
| [0016](../../adr/0016-linguagem-ubiqua.md) | Ubiquitous language | Code, API, MCP, database and docs use the English equivalent of the UI term (company, persona, task, run, gate, flow...), one term per concept; the UI shows pt-BR. See the [glossary](../GLOSSARY.md). |
| [0017](../../adr/0017-modo-trusted-e-limites.md) | Trusted mode: assumptions, limits, mitigations | In `trusted` mode agents and operator share the host as the trust boundary, so the ADR documents the limits (e.g. a local agent can call the API as the human) and the mitigations; `authenticated` removes the main limit. |
| [0018](../../adr/0018-endurecimento-authenticated.md) | Hardening the authenticated mode | After the independent review: an owner must be named or admission lists set on public URLs, argon2id concurrency is capped, `X-Forwarded-For` is trusted only from `HANKO_TRUSTED_PROXIES`, brute force is limited per email, and sessions have a 90-day absolute cap. |
| [0019](../../adr/0019-assinaturas-e-quatro-custos.md) | Subscriptions, four costs, weekly guard | Prices are append-only; each run records real, list, estimated and paid cost (monthly fee prorated by list cost per day); a subscription can block new runs once its weekly usage reaches the guard threshold; the run records where its model choice came from. |
| [0020](../../adr/0020-alertas-e-revisao-automatica.md) | Operational alerts and automatic review | Alerts (silent persona, stuck run, budget near limit) are database state evaluated by a periodic job, shown in the inbox and `/metrics`; runs get friendly names; an optional reviewer persona or alternate model reviews the work before the human gate, records a verdict with a sha256, but never decides. |
| [0021](../../adr/0021-multi-humano-papeis.md) | Multi-human: company roles and invites | Users belong to companies with a role (owner, admin, member, viewer) enforced in the service layer; non-members get 404, never 403; invites are random 7-day tokens stored as hashes and shown as a link (no email is sent); a company never loses its last owner. |
| [0022](../../adr/0022-export-import.md) | Export and import a company | One JSON file (`hanko.company.v1`) with configuration referenced by slug/name/task number, never ids; adapter config is scrubbed of credentials on export and import; runs and logs are opt-in; import always creates a NEW company in one transaction after full validation, keeping relations and task numbering. Export needs admin; import follows the company-creation rule. |
| [0029](../../adr/0029-skills-e-integracoes.md) | Skills and integrations | Reusable `SKILL.md` skills per persona (Claude gets real skills through `--add-dir`; codex/ACP get a prompt index plus the `hanko_skill_get` MCP tool, with size limits); company MCP servers (stdio only if the operator allows it) and HMAC-signed outbound webhooks delivered through a transactional outbox with retries and SSRF blocking; integration secrets are AES-GCM encrypted at rest, never returned (a generated webhook secret is shown once) and never exported. |
| [0023](../../adr/0023-acp-harness-generico.md) | ACP as a generic harness (v1) | One `acp` harness runs any agent that speaks ACP v1 over stdio; the command lives in the persona's `adapter_config`, validated on hire/import. Own stdlib JSON-RPC client; chunks aggregated per message; cost only in USD; permission policy `allow`/`reject`/`read_only` (default; review runs forced); `fs/*` confined to the run directory (writes only with `allow`); cancel via `session/cancel` then kill. `acp` cannot be an alternate review harness. Out of scope: terminal, interactive auth, v2. |

| [0024](../../adr/0024-busca-unica.md) | Company-wide search | One search over tasks, comments, personas, runs, flows and (when a provider exists) company memory: Postgres full-text with generated `tsvector` columns + GIN and no extension (an immutable `hanko_fold()` folds case, accents and punctuation), a last-word prefix, quoted phrases, `-exclude` and `OR`, exact task keys, relevance × recency ranking, and match segments instead of HTML. Readable by every role (ADR-0021); strict per-company scope; memory degrades without failing the search. |
| [0028](../../adr/0028-artefatos-e-metas.md) | Versioned artifacts and goals | Artifacts are immutable versions in Postgres (`artifacts` + `artifact_blobs`), chained by (company, task, name) under an advisory lock; same sha256 and type as the tip returns the existing version; 5 MiB per file and 512 MiB per company by default. Content is served only by `internal/artifactsrv` (nosniff, sandboxing CSP, inline just for plain text, Markdown and raster images, everything else as a download). Text diff between versions, role-checked (viewer reads, member publishes, admin deletes); export/import carries them only with `--with-artifacts`. Goals have a start, target and current value, progress clamped to 0..1, are achieved on crossing the target (activity + informational inbox item), link to tasks and show in the run briefing; MCP `hanko_artifact_put`, `hanko_goal_list`, `hanko_goal_update`. |
| [0031](../../adr/0031-ui-kubo-ds-e-telas-de-paridade.md) | UI on the Kubo DS and parity screens | The UI uses the Kubo DS tokens, font and ring cards as its single source; personas get a glyph from a closed catalog; theme toggle by cookie; the task board, saved views, project/workspace tabs, timeline, live panel, environments/adapters/plugins, export/import and ready-made teams are server-rendered with no new React island. |
| [0033](../../adr/0033-sala-com-varias-personas.md) | Room: one conversation with several personas | A room is a conversation (`kind=room`, no persona of its own) with 2–12 participants; each human message goes to the mentioned personas, to the moderator when nobody is mentioned, or to everyone (`all` mode), through the chat dispatch (status, budgets, weekly guard) with one active run per (conversation, persona) and per-persona coalescing; a refusal by one persona does not drop the others; a reply that mentions another participant wakes it, capped by hops (default 2) and runs per human message; same runs, ledger, roles and polling UI as the chat, with a team activity feed beside the thread; rooms are operational state and are not exported. |
| [0035](../../adr/0035-skills-versoes-fontes-estudio.md) | Skills: versions, sources and test studio | Every change to a skill writes an immutable version (restore creates a new one; personas can pin a version for everything the run receives); public git sources (operator switch `HANKO_SKILL_SOURCES`, https only, host checked before cloning) are cloned shallow without checkout and only `SKILL.md` files are read, never scripts, with selection, hourly auto-update with backoff, local edits kept unless forced, and disconnect keeping or deleting the copies; the studio runs a skill at a fixed version as a system task of a chosen persona that gets only that skill, the input as prompt, no company MCP and no memory, on the normal budget (admin only). |
| [0038](../../adr/0038-plugins-de-terceiros.md) | Third-party plugins | A plugin is an external process speaking line-delimited JSON-RPC 2.0 over stdio, off unless the operator sets `HANKO_PLUGINS_DIR` (never downloaded); a closed list of capabilities is checked by the host on every call (no gate decisions, budgets, auth, secrets or database); the installation owner installs, upgrades (more capabilities wait for approval) and uninstalls, company admins turn it on and configure it (secret fields encrypted, never returned); tools show up in MCP as `plugin_<id>_<tool>` only for companies that turned it on, activity events go through the queue in the fact's transaction, jobs never overlap, and widgets are data (sanitized markdown and tables), never plugin HTML or script. |
| [0037](../../adr/0037-ambientes-remotos-ssh-sandbox.md) | Remote execution environments: SSH and sandbox | Per-company environments (`ssh`, `sandbox`; `local` is implicit and the default) chosen per persona, then company default, then local. Operator switches (`HANKO_ENV_SSH_ALLOW_HOSTS`, `HANKO_ENV_SANDBOX=docker`) are off by default. SSH runs the harness through the system `ssh` with strict host-key checking against a required `known_hosts`, a temporary key file and POSIX-quoted commands, syncing the run directory with tar both ways (confined extraction, deletions mirrored, remote copy kept on failure); the sandbox is a throwaway `docker run` with no capabilities, read-only root and resource limits. Remote harnesses reach MCP through `HANKO_PUBLIC_URL`; keys and variable values are encrypted, never returned and not exported. |
| [0032](../../adr/0032-cards-de-status.md) | Status cards | A living markdown summary of a set of tasks kept by a summarizer persona: the human writes the interest, the persona turns it into 1–10 task filters (`hanko_status_card_set_query`) and keeps the summary (`hanko_status_card_set_summary`), both as system tasks run by the normal run machinery (trigger `status_card`, only the summarizer on the active generation task). A per-minute tick compares task snapshots, applies the policy (manual, interval or reactive with debounce, hourly cap, daily token cap, active hours) and picks full or incremental; a run that ends without writing leaves the card in error with the reason and the last good summary. Viewer reads, member creates and refreshes, the author or an admin archives, admin deletes; not exported. |
| [0034](../../adr/0034-pipelines-cases-revisao-aprendizados.md) | Pipelines, cases, review queue, learnings and decision training | Cases are structured work records, loose or in a pipeline stage (`working`/`review`/`done`/`cancelled`) with fields, approval, persona automation and review destinations; every write needs `expected_version`. Transitions check approver, blockers, children, required fields and strict mode (force + reason, human only). Entering a stage with automation opens a task for the persona with a context package that includes the latest review reasons of that stage ("learnings"). Personas create/upsert cases, suggest and move between working stages, never decide reviews. Review queue with bulk approval, learnings page, and decision examples (gate or case review) snapshotted at the cutoff, exportable as JSONL by admins. Not in export/import yet. |
